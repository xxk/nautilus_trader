# 国内期权接入缺口评估

**创建日期**：2026-03-27  
**最后更新**：2026-03-27  
**状态**：已分析

---

## 一句话结论

Nautilus 当前**适合做期权策略框架底座**，但若目标是接入中国境内 ETF 期权或商品期权，缺口不在策略层，而在 **venue adapter、合约解析、行情交易映射、结算与交易所规则** 这一整层接入基础设施。

换句话说：

1. 期权模型、组合模型、Greeks、期权链、回测框架这些“通用能力”大部分已经有。
2. 国内期权要真正跑起来，核心工作是补一条新的中国市场接入链路，而不是只写一个策略。

---

## 已有能力：哪些不用重写

以下能力在 Nautilus 当前仓库里已经存在，可直接作为国内期权接入底座复用。

### 1. 通用期权合约模型已具备

 `OptionContract` 已是通用期权合约对象，包含：标的、看涨看跌、行权价、到期时间、乘数、最小价格变动、保证金/手续费扩展字段。

这意味着国内 ETF 期权、商品期权**不需要重新发明期权对象模型**，重点是把中国交易所返回的数据正确映射进这些对象。

### 2. 策略层已经支持期权事件

策略接口已支持：

- `on_option_greeks`
- `on_option_chain`

因此，Greeks 驱动、期权链扫描、波动率监控这类策略入口已经有，**不需要从零设计策略 API**。

### 3. Greeks 与期权链基础设施已具备

仓库已提供两套能力：

1. venue 提供的实时 Greeks 接入接口
2. 本地 `GreeksCalculator` 计算链路

对于国内市场这点很关键，因为国内很多源头不会像 Deribit 那样天然推全套 Greeks。即使没有 venue 级 Greeks，也可以先靠本地计算补上第一版研究与风控能力。

### 4. 回测与序列化基础设施可复用

当前数据引擎、回测数据客户端、缓存、Arrow/Parquet 序列化、Instrument 持久化这套底层都已经存在。接国内期权时，主要是把中国市场数据喂进现有框架，而不是重写一套回测内核。

---

## 当前直接缺口：哪些模块必须新增或重做

## 1. Venue Adapter 缺失

当前仓库能看到期权相关 live 支持集中在国际/加密 venue，例如 Deribit、IB。没有现成的：

- CTP adapter
- 上交所 / 深交所期权 adapter
- 中国期货期权专用 adapter

这意味着如果要接国内期权，至少要新增一条完整 adapter 链路，通常包括：

1. `InstrumentProvider`
2. `LiveMarketDataClient`
3. `LiveExecutionClient`
4. 对应配置、工厂、测试夹具

对于商品期权，第一优先通常是 CTP；对于 ETF 期权，还要区分你拿的是柜台接口、券商接口，还是中间商行情/交易网关。

## 2. 国内合约解析与符号体系缺失

Nautilus 的期权模型是通用的，但**国内合约命名和解析规则并没有现成落地**。需要补：

1. 国内期权 `raw_symbol -> InstrumentId` 规则
2. 交易所代码与 venue/MIC 映射
3. ETF 期权与商品期权不同的合约字段解析
4. 认购/认沽、行权价、到期月、合约乘数、最小报价单位等映射

尤其是以下差异必须单独处理：

1. ETF 期权更接近证券类市场结构
2. 商品期权更接近期货市场结构，并受夜盘、交易日、平今平昨等规则影响

## 3. 国内行情语义映射缺失

框架已有 `QuoteTick`、`TradeTick`、`OrderBook`、`Bar` 等标准数据对象，但国内期权接入还缺：

1. 国内源头字段到标准事件的映射
2. 交易状态、集合竞价、临停、收盘状态映射
3. 夜盘与交易日跨自然日处理
4. 涨跌停、昨结、今结、持仓量等字段是否进入 `info` 或扩展数据

如果目标是商品期权，这里复杂度明显高于普通股票行情接入，因为夜盘、交易日切换、结算价口径会直接影响回测和实盘一致性。

## 4. 执行链路与订单语义缺失

执行不是“把买卖单发出去”这么简单。国内期权至少要补这些语义：

1. 报单、撤单、成交、拒单、废单、部成部撤事件映射
2. 商品期权的开平、平今、平昨语义
3. 交易所/柜台返回的本地单号、成交号、报单状态映射
4. 断线重连后的委托与持仓重建

商品期权若走 CTP，这部分通常是最难的一段之一，因为开平语义和交易所规则不是美国券商股票/期权那种统一抽象可以直接套用。

## 5. 结算、保证金与中国市场特有规则未落地

虽然 Nautilus 已有通用 margin account 和 premium-based instrument 处理，但国内期权要生产可用，还缺：

1. 商品期权组合保证金/交易所保证金规则接入
2. ETF 期权备兑、保证金口径、行权交收规则接入
3. 行权、指派、到期自动失效/自动行权规则
4. 日终结算、结算确认、账单对账

这里是“研究可跑”和“生产可用”的分水岭。很多策略在回测里能跑，不代表实盘账务和风控是对的。

## 6. 历史数据与回测数据源仍需单独补齐

框架本身支持回测，但国内期权要真正可研究，还需要一条可落地的数据准备链：

1. 历史 tick / quote / trade / bar 数据采集
2. 历史合约主数据归档
3. 到期摘牌后的历史 instrument 可回放
4. 国内期权 Greeks 若无源头字段，是否离线回算并持久化

如果没有这条链，期权策略只能在 live 里跑实验，无法形成稳定研究闭环。

---

## 按市场类型拆开看：ETF 期权与商品期权缺口并不一样

## ETF 期权

更像证券类市场，通常重点在：

1. 券商/柜台接入方式
2. 合约主数据维护
3. 行权交收与账户限制
4. 风控与资金口径

相对商品期权，夜盘和平今平昨问题较轻，但账户、权限、行权、备兑等规则更重要。

## 商品期权

更像期货市场扩展，通常重点在：

1. CTP 或期货公司柜台接入
2. 开平今昨语义
3. 夜盘、交易日、结算价
4. 组合保证金与交易所规则

如果目标是上期所、大商所、郑商所、中金所、广期所商品期权，接入难点明显高于 ETF 期权。

## 建议按模块分阶段落地

## Phase 0：只做研究底座验证

目标：先证明 Nautilus 的通用期权能力可以承载中国期权策略研究。

建议动作：

1. 用静态主数据手工构造一批国内期权 `OptionContract`
2. 导入历史 bar / quote 数据
3. 用本地 `GreeksCalculator` 跑最小 Greeks 研究链路
4. 验证策略层 `on_option_chain` / `on_option_greeks` 是否满足需求

这一步不碰 live adapter，成本最低。

## Phase 1：先补数据链路，不先补交易

目标：先拿到国内期权实时/历史数据，做稳定研究与仿真。

需要新增：

1. 国内 `InstrumentProvider`
2. `LiveMarketDataClient`
3. 国内合约解析、symbol 映射、交易日历与 session 处理

到这一步，已可以做较完整的监控、信号研究、回放与 paper trading。

## Phase 2：再补执行链路

目标：支持真实报撤单、成交回报、账户同步。

需要新增：

1. `LiveExecutionClient`
2. 订单状态与成交回报映射
3. 账户、持仓、保证金同步
4. 断线重连、恢复与对账

## Phase 3：补齐生产规则

目标：让国内期权实盘具备账务和规则正确性。

需要补齐：

1. 行权/指派
2. 结算确认
3. 组合保证金
4. 日终账务校验
5. 异常恢复与补单补状态

---

## 结论：缺口清单

如果目标是“用 Nautilus 做国内期权策略”，当前最核心的缺口排序如下：

1. **第一缺口：国内 venue adapter**
2. **第二缺口：国内合约与 symbol 解析**
3. **第三缺口：国内行情与交易状态语义映射**
4. **第四缺口：执行链路与开平今昨/回报恢复**
5. **第五缺口：结算、保证金、行权等中国市场规则**
6. **第六缺口：历史数据与研究数据资产沉淀**

而以下部分不是主要瓶颈：

1. 期权对象模型
2. 期权链与 Greeks 的通用框架
3. 事件驱动策略接口
4. 通用回测与缓存持久化基础设施

所以，Nautilus 对国内期权不是“不适合”，而是**适合作为底座，但不适合在没有 adapter 建设投入的前提下直接落地国内期权实盘**。

---

## 粗粒度工作量判断

如果以商品期权 CTP 为目标，当前更合理的预估是：

1. 仅数据链路：中等规模工作
2. 数据 + 基础交易：明显不是小改动
3. 生产可用：需要补齐交易所规则、恢复、结算与验收体系

因此，建议默认按“新接入项目”而不是“加一个小 adapter”来立项。
