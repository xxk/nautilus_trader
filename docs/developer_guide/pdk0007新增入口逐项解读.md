## 1. run_ratio_spread_1x2_qty3.py

### 定位

- 文件：`examples/live/interactive_brokers/notebooks/run_ratio_spread_1x2_qty3.py`
- 形态：Jupytext 导出的 `.py` 脚本，但本质是一个可直接运行的 live 验证入口。
- 核心类：`RatioSpreadTestConfig`、`RatioSpreadTestStrategy`

### 它在做什么

这个脚本不是在做 alpha 交易，而是在验证 IB 组合单执行链路是否正确支持 `1x2 ratio spread`。

脚本先手工构造两个腿的 `InstrumentId`，再用 `InstrumentId.new_spread(...)` 生成 spread 合约，然后：

1. 在 `on_start()` 里调用 `request_instrument(self.config.spread_instrument_id)`，测试 spread 合约能否动态加载。
2. 在 `on_instrument()` 里一旦拿到 spread 合约，就订阅 quote ticks。
3. 紧接着调用 `_place_ratio_spread_order()`，下一个 `BUY`、`quantity=3`、`TimeInForce.DAY` 的 market combo order。
4. 在 `on_order_submitted()`、`on_order_accepted()`、`on_order_filled()` 里完整记录订单状态与成交。
5. 在 `_analyze_fill()` 和 `on_stop()` 中核对实际成交数量是否符合 “买 3、卖 6” 的比例预期。

### 关键行为

最有价值的点有 4 个：

1. **动态合约加载**：不是预先把 spread ID 写进 provider，而是运行中请求，适合验证组合合约发现链路。
2. **成交归因分析**：它会区分当前 fill 是 spread-level 还是 leg-level，并打印成交方向、数量、价格、佣金与 trade id。
3. **投资组合回看**：每次成交后会遍历 `cache.positions_open()` 和 `cache.positions_closed()`，核对组合腿最终仓位。
4. **自动收口**：`auto_stop_node(node, delay_seconds=60)` 会在 60 秒后自动停止节点，适合短时 paper-trading 验证。

### 工程价值

它最值得借鉴的不是“策略逻辑”，而是 **组合执行验证脚本模板**：

1. 如何动态请求复杂合约。
2. 如何把下单、接单、成交、持仓核对串成一条验收链。
3. 如何在 live 环境下做“小而闭环”的执行实验，而不是直接写成长期运行策略。

### 迁移建议

适合迁移：

1. `request_instrument -> on_instrument -> 下单 -> fill 分析 -> portfolio 核对` 这一整条验证框架。
2. ratio spread / combo order 的验收脚本写法。

不适合直接照搬：

1. 它默认是 market combo order，风险控制很弱。
2. 它的目标是验证执行正确性，不是做交易决策。

## 2. polymarket_market_maker.py

### 定位

- 文件：`examples/live/polymarket/polymarket_market_maker.py`
- 形态：新增 venue 入口，内嵌策略类。
- 核心类：`TOBQuoterConfig`、`TOBQuoter`

### 它在做什么

这是一个面向 Polymarket 的最优盘口跟价做市脚本。它通过 `get_polymarket_instrument_id(condition_id, token_id)` 定位单个 binary option 市场，然后在 live 节点里同时接入 Polymarket 的 data 和 exec client。

策略在 `on_start()` 里：

1. 从 cache 取 instrument。
2. 订阅 `quote ticks`、`trade ticks`、`order book deltas`。

策略在 `on_order_book_deltas()` 和 `on_quote_tick()` 里都会调用 `maintain_orders(best_bid, best_ask)`，核心动作是：

1. 如果没有买单，就在 `best_bid` 创建买单。
2. 如果没有卖单，就在 `best_ask` 创建卖单。
3. 如果已有挂单价格不再等于当前最优价，就撤掉旧单，再挂新单。

### 关键行为

这个入口最重要的不是复杂算法，而是把 Polymarket 这个特殊 venue 的约束显式写了出来：

1. `post_only=False`，因为脚本里直接说明 Polymarket 不支持 `post_only`。
2. `LiveRiskEngineConfig(bypass=True)`，说明这个入口更偏适配验证而非正式风控闭环。
3. `min_size = Decimal(5)`，实际下单量取 `max(min_size, trade_size)`，反映了 venue 侧最小交易单位约束。
4. `on_stop()` 会 `cancel_all_orders()` 并 `close_all_positions()`，说明它默认是“强收口”脚本。
5. `enable_buys` / `enable_sells` / `dry_run` 都在 config 中显式暴露，便于切换成单边或空跑模式。

### 工程价值

它是一个 **prediction market / binary option 场景的 quoter 模板**，价值主要在：

1. 展示 Polymarket 适配层如何进入 Nautilus 的标准 `TradingNode`。
2. 说明事件驱动型做市在“无 bar、以 book/quote 为主”的 venue 上该如何接数据。
3. 把“最优价跟单”逻辑压缩到一个很小的策略类里，便于二次改造成 inventory skew 或双 token 对冲版本。

### 迁移建议

适合迁移：

1. `maintain_orders()` 这种最小可运行 quoter 骨架。
2. Polymarket instrument 解析与订阅启动方式。

不适合直接照搬：

1. 风控是 bypass 状态。
2. 只是 join best bid/ask，没有库存控制，也没有价差保护。

## 3. coinbase_intx_quoter.py

### 定位

- 文件：`examples/live/coinbase_intx/coinbase_intx_quoter.py`
- 形态：新增 venue 入口，内嵌策略类。
- 核心类：`TOBQuoterConfig`、`TOBQuoter`

### 它在做什么

这是一个面向 Coinbase International perpetual 市场的被动跟价脚本。默认 instrument 是 `BTC-PERP.COINBASE_INTX`，策略参数里最关键的是 `offset_ticks`、`trade_size` 与 `dry_run`。

它在 `on_start()` 里：

1. 从 cache 拿 instrument。
2. 订阅 `quote ticks` 和 `trade ticks`。

它在 `on_quote_tick()` 里直接调用 `maintain_orders(tick.bid_price, tick.ask_price)`。挂单逻辑不是直接 join 当前盘口，而是：

1. 买单价格 = `best_bid - offset_ticks * price_increment`
2. 卖单价格 = `best_ask + offset_ticks * price_increment`

### 关键行为

这个脚本最有价值的地方在于它把 Coinbase Intx 的一些 venue 约束写实了：

1. `use_uuid_client_order_ids=True` 被标成“必要”，说明 client order id 规则和其他 venue 不同。
2. 限价单使用 `TimeInForce.GTD`，并设置 `expire_time = now + 1 minute`。
3. 限价单使用 `post_only=True`，强调它更偏 maker-only 报价。
4. `on_stop()` 关闭仓位时使用 `TimeInForce.IOC`，脚本里直接写了这是 Coinbase Intx 所需。
5. 它虽然定义了 `on_order_book_deltas()`，但默认主要依赖 `quote ticks` 驱动报价更新，因此实现更轻。

### 工程价值

它是一个 **适配型 passive quoter 模板**，相比 Polymarket 版本更偏标准交易所做市：

1. 有显式 `offset_ticks`，可以作为安全报价距离。
2. 有 `post_only`，更接近真实 maker 策略骨架。
3. 订单生命周期比 Polymarket 版本更规范，适合扩展成 cancel-replace 与 inventory-aware quoter。

### 迁移建议

适合迁移：

1. `offset_ticks + post_only + GTD` 这套被动挂单框架。
2. venue 专属 order/TIF 约束的显式落地方式。

不适合直接照搬：

1. 当前 `maintain_orders()` 对已有 open order 的处理偏保守，很多分支只是 `pass`，还没做真正 cancel-replace。
2. 仍然没有库存控制和波动过滤。

## 4. binance_spot_orderbook_imbalance_rust.py

### 定位

- 文件：`examples/live/binance/binance_spot_orderbook_imbalance_rust.py`
- 形态：新增 live 入口。
- 复用策略体：`nautilus_trader.examples.strategies.orderbook_imbalance_rust.OrderBookImbalance`

### 它在做什么

这个入口把上游已经存在的 Rust 版本盘口不平衡策略接到 Binance spot live 上。默认 instrument 是 `ETHUSDT.BINANCE`，策略配置里核心只保留：

1. `instrument_id`
2. `external_order_claims`
3. `max_trade_size`

其策略体内部是：

1. 用 `nautilus_pyo3.OrderBook` 和 `BookImbalanceRatio` 保存盘口状态与失衡指标。
2. 在 `on_order_book_deltas()` 中手工 `apply_deltas()`，再更新不平衡指标。
3. 一旦 `ratio < trigger_imbalance_ratio` 且较大一侧量超过阈值，就用 `FOK` 限价单去 hit 对手盘。

### 工程价值

这个脚本的重要性不在于逻辑新，而在于它证明了：

1. Rust 指标/盘口对象可以直接被 live Binance 入口复用。
2. live 版 `orderbook_imbalance_rust` 入口是独立存在的，不只是 backtest 示例。
3. 这类策略更适合高频研究，因为它把盘口增量处理放到了 Rust 侧。

### 迁移建议

适合迁移：

1. Rust 盘口策略的 live 装配方式。
2. `managed=False + pyo3_conversion=True` 这一类手工 book 更新思路。

不适合直接照搬：

1. 这是触发式 hit 策略，不是做市策略。
2. 仍然属于演示级参数，没有针对真实滑点和手续费做约束。

## 5. binance_spot_market_maker.py

### 定位

- 文件：`examples/live/binance/binance_spot_market_maker.py`
- 形态：新增 live 入口。
- 复用策略体：`VolatilityMarketMaker`

### 它在做什么

这是把官方 `VolatilityMarketMaker` 接到 Binance spot 的标准 live 入口。默认 instrument 是 `ETHUSDT.BINANCE`，bar 使用 `ETHUSDT.BINANCE-1-MINUTE-LAST-INTERNAL`。

关键配置：

1. `account_type=BinanceAccountType.SPOT`
2. `instrument_provider=InstrumentProviderConfig(load_all=True)`
3. `trade_size=Decimal("0.010")`
4. `atr_period=20`
5. `atr_multiple=6.0`

### 工程价值

这个入口最大的价值是 **把官方波动率做市策略落到 Binance 现货环境**，补齐了当前本地仓库没有的 venue 示例。

它适合回答两个问题：

1. 官方 `VolatilityMarketMaker` 在现货 venue 上推荐怎样接 `bar_type`。
2. 现货做市入口的最小 node 装配长什么样。

### 迁移建议

适合迁移：

1. Binance spot live node 的最小配置骨架。
2. `VolatilityMarketMaker` 在现货场景下的参数模板。

不适合单独高估：

1. 它新增的是入口，不是策略体本身。

## 6. binance_futures_market_maker.py

### 定位

- 文件：`examples/live/binance/binance_futures_market_maker.py`
- 形态：新增 live 入口。
- 复用策略体：`VolatilityMarketMaker`

### 它在做什么

这个脚本把官方波动率做市策略接到 Binance futures。和现货版相比，它关注的是 perpetual / futures 场景下的 node 装配与风控对接。

从入口结构看，它仍然是：

1. 初始化 Binance data/exec client。
2. 用 `VolatilityMarketMakerConfig` 绑定 futures instrument 与 bar。
3. 把策略加入 `TradingNode` 后直接 `node.run()`。

### 工程价值

这个入口的价值主要是 venue 维度：

1. 说明同一官方策略体可以较平滑地迁移到 Binance futures。
2. 给出 futures live 做市的最小装配模板。
3. 方便拿来和 `binance_spot_market_maker.py` 做 spot/futures 对照。

### 迁移建议

适合迁移：

1. 同策略体跨现货/合约 venue 的配置拆分方式。

限制：

1. 它仍是官方策略体的 venue 包装层，不提供新的 alpha 逻辑。

## 8. polymarket_ema_cross.py

### 定位

- 文件：`examples/live/polymarket/polymarket_ema_cross.py`
- 形态：新增 live 入口。
- 复用策略体：`EMACross`

### 它在做什么

这个脚本把官方 `EMACross` 接到了 Polymarket，但不是直接拿 bar 喂策略，而是做了一层 venue 适配：

1. 因为 Polymarket 不提供标准历史 bar，脚本把 `bar_type` 设成 `1-SECOND-MID-INTERNAL`。
2. 也就是先用 quote ticks 合成内部 mid-price bars，再驱动 EMA 交叉。
3. `request_bars=False`，说明不依赖历史 bar 回补。
4. `subscribe_quote_ticks=True`、`subscribe_trade_ticks=True`，说明数据源主要还是 tick。
5. 下单使用 `TimeInForce.IOC`，并且 `order_quantity_precision=POLYMARKET_MAX_PRECISION_TAKER`。

### 工程价值

这个入口的价值比前几个“纯 venue 包装”更高，因为它展示了 **官方 bar 驱动策略如何迁移到无原生 bar 的 prediction market**：

1. 通过内部合成的 mid bars 复用现有策略体。
2. 明确写出 Polymarket 不支持历史 bars、stop 只做 close-position 型收口等限制。
3. 这是一个很好的“策略体不改，只改数据适配层”的例子。

### 迁移建议

适合迁移：

1. quote -> internal mid bar -> indicator strategy 这条适配链。
2. 针对非传统 venue 的 bar 替代方案。

不适合直接照搬：

1. EMA 周期非常短，明显是为了 prediction market 的快节奏演示，不是稳健参数。

## 分类结论

### 最值得复用的 3 类资产

1. **执行验收脚本模板**：`run_ratio_spread_1x2_qty3.py`
2. **内嵌 quoter 模板**：`polymarket_market_maker.py`、`coinbase_intx_quoter.py`
3. **官方策略的 venue 迁移模板**：`binance_*_market_maker.py`、`binance_spot_orderbook_imbalance_rust.py`、`polymarket_ema_cross.py`

### 最值得继续深挖的 3 个方向

1. 把 `coinbase_intx_quoter.py` 和 `polymarket_market_maker.py` 对比成一份“venue 约束差异表”。
2. 把 `run_ratio_spread_1x2_qty3.py` 抽象成“组合执行验收模板”。
3. 把 `polymarket_ema_cross.py` 归纳成“无 bar venue 适配策略体”的通用套路。
